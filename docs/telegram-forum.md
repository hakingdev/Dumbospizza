# Telegram: группа заказов в режиме форума

Карточка заказа живёт в теме своего статуса и «переезжает» между темами при
смене статуса. Кухня смотрит в «🔥 Готовится», курьер — в «📦 Готов к доставке»,
и ни один заказ не теряется в общей ленте.

## Темы

| Тема | Статусы заказа | Конфиг |
| --- | --- | --- |
| 🔥 Готовится | `new`, `preparing` | `telegramTopicCooking` / `TELEGRAM_TOPIC_COOKING` |
| 📦 Готов к доставке | `ready_for_delivery` | `telegramTopicReady` / `TELEGRAM_TOPIC_READY` |
| 🚗 В пути | `delivering` | `telegramTopicOnTheWay` / `TELEGRAM_TOPIC_ON_THE_WAY` |
| ✅ Доставлен | `completed` | `telegramTopicDelivered` / `TELEGRAM_TOPIC_DELIVERED` |
| ❌ Отменён (необязательно) | `cancelled` | `telegramTopicCancelled` / `TELEGRAM_TOPIC_CANCELLED` |

`new` и `preparing` делят одну тему намеренно: для кухни это одно состояние,
а лишний переезд рвёт ленту и жжёт лимит сообщений. Отменённые по умолчанию
уезжают в архивную тему «Доставлен» — отдельная тема опциональна.

Темы создаются **один раз** скриптом, их id хранятся в конфиге. Бот не создаёт
и не ищет темы при заказе.

## Включение

1. В группе включить режим Topics и выдать боту права **Manage Topics**,
   **Delete Messages**, **Post Messages**.
2. Таблица карточек:
   ```bash
   node scripts/apply-order-cards-migration.mjs
   ```
3. Создать темы и записать их id (в `storeSettings`):
   ```bash
   node scripts/telegram-topics.mjs create --save
   ```
   Проверить, что получилось: `node scripts/telegram-topics.mjs check`.
   ⚠️ Bot API не умеет перечислять темы — повторный `create` создаст дубли.
4. Разложить активные заказы по темам (сначала вхолостую):
   ```bash
   npx tsx scripts/migrate-telegram-forum-cards.ts --dry-run
   npx tsx scripts/migrate-telegram-forum-cards.ts
   ```
   Закрытые (`completed`/`cancelled`) и драфты не трогаются.

Пока `telegramForumEnabled` выключен **или** не заданы все четыре обязательные
темы, бот работает по-старому: одно сообщение на заказ, редактируемое на месте.
Это защита от «включили флаг, темы не создали» — заказы не должны теряться.

## Как устроен переезд

Telegram не умеет переносить сообщение между темами, поэтому переезд — это:

1. `sendMessage` в новую тему (новый текст + клавиатура под новый статус);
2. запись в `order_cards`: карточка теперь здесь;
3. `deleteMessage` старой карточки.

Отправка строго первая: пока новая карточка не подтверждена, старую трогать
нельзя. Запись в БД стоит между отправкой и удалением осознанно — падение после
удаления, но до записи оставило бы БД со ссылкой на удалённое сообщение. Провал
удаления логируется и **не** откатывает переезд: лучше дубль, чем потерянный
заказ.

Если целевая тема совпадает с текущей (`new` → `preparing`), карточка правится
на месте — без пересылки.

### Двойной тап

Два рубежа:

* `withOrderLock` — блокировка по заказу внутри процесса; ловит типовой случай,
  когда оба клика приходят в один инстанс функции;
* CAS-апдейт `UPDATE order_cards SET status=… WHERE order_id=… AND status=<ожидаемый>` —
  настоящий рубеж: работает между инстансами Vercel и между ботом и админкой.

Из двух кликов строку получает ровно один вызов, второму возвращается `null` →
отправлять новую карточку он не имеет права. Если статус в БД уже целевой —
no-op, ни одного сообщения.

### Ошибки

| Ситуация | Поведение |
| --- | --- |
| `message to delete not found` / `message can't be deleted` | игнорируем, переезд считается успешным |
| `429` с `retry_after` | очередь ждёт ровно столько и повторяет |
| сеть / `5xx` | экспоненциальный backoff, до 4 попыток |
| `TOPIC_CLOSED` | `reopenForumTopic` и повтор отправки |
| `sendMessage` упал | старая карточка НЕ удаляется, статус карточки откатывается, оператору — «Не удалось обновить статус, попробуйте ещё раз» |

## Очередь исходящих

Все действия в группу идут через одну очередь (`lib/telegram/outbox.ts`):
не чаще ~1 действия в секунду, с приоритетами. Новый заказ (`priority 0`)
обгоняет переезды (`priority 10`) — поток переездов не имеет права задержать
доставку заказа на кухню.

Очередь живёт в памяти инстанса функции, поэтому ограничение частоты — «на
инстанс». Пики идут внутри одного вебхук-вызова (переезд = 2–3 действия), а
межинстансные 429 переигрываются `retry_after`. Все задачи дожидаются до ответа
на webhook: после ответа Vercel замораживает функцию.

## Уведомления

Переезды беззвучные (`disable_notification: true`), кроме двух:

* **📦 Готов к доставке** — сигнал курьеру;
* **✅ Доставлен** — заказ закрыт.

Отмена уходит молча, хотя по умолчанию и лежит в той же теме, что «Доставлен»:
звук привязан к статусу карточки, а не к теме. Настраивается
`telegramCardSoundStatuses` / `TELEGRAM_CARD_SOUND_STATUSES` (список статусов
через запятую, по умолчанию `ready,delivered`). Новый заказ всегда со звуком.

## Кнопки

Только релевантные текущему статусу:

| Статус | Кнопки |
| --- | --- |
| 🔥 Готовится | `🚚 Доставка` · `⏱ Время готовности` · `⏳ Продлить` · `🖨 Чек` · `❌ Отменить` |
| 📦 Готов | `✅ Доставлен` · `🧍 Назначить курьера` · `⚠️ Проблема` · `↩️ Вернуть в готовку` |
| 🚗 В пути | `✅ Доставлен` · `⚠️ Проблема с доставкой` |
| ✅ Доставлен | — (первые 10 мин: `↩️ Вернуть в путь`) |
| ❌ Отменён | — (первые 10 мин: `↩️ Вернуть в готовку`) |

Время готовности, продление, печать чека и отмена есть **только на карточке
«Готовится»**: это операции по заказу, который ещё на кухне. Дальше по маршруту
нужен один жест — «Доставлен». Ряд `⏱ / ⏳ / 🖨` отключается флагом
`TELEGRAM_CARD_HIDE_UTILITY_BUTTONS=true`, `❌ Отменить` остаётся всегда.

Кнопка «🚚 Доставка» названа по теме, а не по статусу: у ресторана готовность и
передача курьеру — один шаг, две кнопки под одну тему читались как дубль.
Статус за ней прежний, `ready_for_delivery`, поэтому гость получает корректное
«заказ готов», а не преждевременное «в пути». Промежуточного «Курьер забрал» на
карточках нет; статус `delivering` остаётся достижимым из админки и у него своя
клавиатура.

Плюс служебный ряд на активных статусах: `🖨 Чек`, `⏳ Продлить` — это не
переходы статуса, а действия, которые ресторану нужны на любой стадии.
Отключается флагом `TELEGRAM_CARD_HIDE_UTILITY_BUTTONS=true`.

Кнопки статуса используют **те же** `callback_data` (`status_*`), что и обычный
режим: за ними вся существующая логика — сохранение заказа, баллы лояльности,
WhatsApp клиенту. Форум меняет расположение карточки, а не доменную логику.

Окно отката (10 мин) проверяется **дважды**: кнопка рисуется только внутри окна,
но карточка не перерисовывается по таймеру, поэтому срок проверяется ещё раз
при клике — протухшая кнопка отвечает отказом и исчезает.

### Назначить курьера

Список имён из `telegramCouriers` / `TELEGRAM_COURIERS` (через запятую) плюс
«🙋 Я забираю» — подставляет имя нажавшего из Telegram. Имя пишется в
`order_cards.courier` и показывается в шапке карточки.

### Проблема с доставкой

Причина (не дозвонился / нет дома / неверный адрес / отказ / другое) пишется в
хронологию карточки и дублируется коротким сообщением **со звуком** в ту же
тему: правка карточки беззвучна, а проблему на дороге должны увидеть сразу.
Карточка при этом не переезжает — заказ по-прежнему в пути.

## Таблица `order_cards`

| Колонка | Смысл |
| --- | --- |
| `order_id` (PK) | `orders.id` |
| `order_number` | номер из `callback_data` кнопок (уникальный индекс) |
| `chat_id`, `message_id`, `topic_id` | где именно лежит карточка сейчас |
| `status` | состояние карточки (`cooking` … `cancelled`) |
| `courier` | назначенный курьер |
| `status_history` | `[{status, timestamp, note?}]` — хронология внизу карточки |
| `created_at`, `updated_at` | служебные |

`orders.telegram_message_id` держится синхронно с карточкой: на него смотрят
легаси-пути, иначе после переезда там остался бы id удалённого сообщения.
